# Управляемые действия (AMS AI Residency, задание 2, направление B)

Небольшой изолированный сервис: получает цель, строит ограниченный план и выполняет его с mock-системой
**только через policy и gateway**. Поддерживает режимы `read_only`, `confirm` и (бонус) `policy_automated`.
Каждый значимый переход записывается в аудит.

## Запуск (одна команда)

```bash
docker compose up --build
```

Откройте http://localhost:3000. На странице выберите сценарий и нажмите «Создать задачу».
Реальная LLM и платные API не нужны: по умолчанию работает детерминированный `MockPlanner`.

Без Docker (Node 20+):

```bash
npm install
npm run build && npm start        # http://localhost:3000
```

## Тесты (ровно три)

```bash
npm install
npm test
```

| Тест | Что проверяет |
|---|---|
| основной сценарий | состояния `QUEUED→PLANNING→RUNNING→WAITING_CONFIRMATION→RUNNING→COMPLETED`, результат, поля аудита |
| безопасный отказ | запись в `read_only`, роль `viewer`, неизвестный инструмент, лишние аргументы, мусорный план, чужой workspace, лимит tool calls, инъекция в tool output |
| защита от дубля | повтор `task_id`, конфликт `task_id`, повторное подтверждение: ровно одно действие |

## Демо-сценарий (для видео до 3 минут)

1. Сценарий 3 «Запись в confirm» → `WAITING_CONFIRMATION`, видны инструмент и аргументы → «Подтвердить» → `COMPLETED`.
2. «Подтвердить повторно» → `409 CONFIRMATION_ALREADY_USED`, действие одно. «Отправить повторно» → `duplicate=true`, событий не прибавилось.
3. Сценарий 2 «Запись в read_only» → блокировка до вызова инструмента.
4. Сценарий 4 «ИИ выдумал инструмент» → отклонён gateway (`UNKNOWN_TOOL`).
5. Показать журнал аудита и `trace_id`.

## Схема компонентов

```
React-панель (web/) ──HTTP──► API (src/server.ts: только HTTP и валидация входа)
                                   │
                                   ▼
                          TaskService (src/service.ts)
                          состояния, лимиты, идемпотентность, аудит
                     ┌─────────┼──────────────┬─────────────────┐
                     ▼         ▼              ▼                 ▼
                 Planner    ToolGateway ──► PolicyEngine     Storage (SQLite)
               (Mock | LLM)  (allowlist,     (mode, role,     tasks, events,
               план = данные  схемы args)     лимиты)         pending_actions
                                 │
                                 ▼
                         RecordsSystem (интерфейс)
                         └─ SqliteRecordsSystem (mock)
```

Ключевые правила:

- Planner возвращает **только данные** (план). Он не имеет ссылок на инструменты. План проверяется Zod-схемой `PlanSchema`.
- Порядок проверок в gateway: инструмент известен → аргументы валидны (`.strict()`) → policy → исполнение.
- `workspace_id` для инструментов берётся из задачи, а не из аргументов планировщика.
- Подтверждение одноразовое: атомарный `UPDATE ... WHERE status='pending'`; исполняется сохранённое в БД действие, а не то, что прислал клиент.
- Запись идемпотентна на уровне БД: `UNIQUE(idempotency_key)` где ключ = `task_id:шаг`.
- Задачи, события и подтверждения хранятся в SQLite и доступны после перезапуска.

## API

| Метод | Маршрут | Назначение |
|---|---|---|
| POST | `/tasks` | Создать задачу (`201`), повтор того же `task_id` даёт `200` и `duplicate: true` |
| GET | `/tasks/{id}` | Состояние, результат, `limits_used`, ожидающее действие |
| GET | `/tasks/{id}/events` | Упорядоченный журнал аудита |
| POST | `/tasks/{id}/confirm` | Подтвердить (`{"confirmation_id": "...", "approve": true}`) |
| POST | `/tasks/{id}/cancel` | Остановить дальнейшее выполнение |

Пример:

```bash
curl -s localhost:3000/tasks -H 'content-type: application/json' -d '{
  "workspace_id":"demo-a","user_id":"user-7","role":"operator","mode":"confirm",
  "goal":"Create a follow-up for the renewal",
  "context":{"query":"Northwind","record_id":"rec-1","note":"Call about pricing"}}'
```

## Точки подключения (без переписывания доменной логики)

Всё собирается в одном месте: `src/runtime.ts`.

- **Реальная модель**: реализовать интерфейс `Planner` (`src/planner.ts`). Заготовка `LlmPlanner` включается через `PLANNER=llm` и `LLM_BASE_URL/LLM_API_KEY/LLM_MODEL`. Ответ модели проходит ту же схему и gateway. В прототипе этот адаптер не запускался.
- **Реальная система вместо mock**: реализовать интерфейс `RecordsSystem` (`src/mock-system.ts`).
- **Корпоративная аутентификация**: сейчас `user_id` и `role` приходят в теле запроса (заглушка). В проде их берёт из проверенного токена слой перед `TaskService` (middleware в `src/server.ts`).
- **Внешнее хранилище**: заменить класс `Storage` (`src/storage.ts`), сервис зависит только от его методов.

## Конфигурация

Файл `config/default.json` (лимиты по умолчанию и максимальные, allowlist для `policy_automated`) + переменные окружения (`.env.example`).
Секреты в репозитории не хранятся. Схема БД создаётся автоматически при старте.

## Выбор стека

TypeScript + Fastify + better-sqlite3 + Zod + Vitest + React (Vite): один язык на сервере и клиенте; Zod даёт runtime-валидацию недоверенного вывода ИИ;
SQLite встраивается и не требует отдельного сервиса; React-панель только показывает состояние из БД и не участвует в выполнении.

## Допущения

- Отказ политики (запись в `read_only`, неизвестный инструмент) останавливает задачу со статусом `FAILED` и кодом причины; сделанные ранее чтения сохраняются в результате.
- Время ожидания подтверждения не входит в `max_runtime_seconds`.
- Лимиты из запроса ограничиваются серверными максимумами из конфигурации.
- После рестарта задачи в `PLANNING/RUNNING` помечаются `FAILED (INTERRUPTED)`, `WAITING_CONFIRMATION` остаются и подтверждаются как раньше.
- Demo-данные полностью вымышленные, персональных данных нет. Флаг `context.simulate` в `MockPlanner` имитирует ошибки ИИ только для демонстрации.

## Три угрозы

1. **Prompt injection через tool output.** Текст из данных не участвует в решениях: `PolicyEngine` не читает вывод инструментов, а результат только сохраняется. Подозрительный вывод помечается в аудите (`suspicious_output`).
2. **Ошибочный или враждебный план ИИ** (несуществующий инструмент, чужой `workspace_id`, лишние аргументы). Схема плана + gateway с allowlist и `.strict()`-схемами.
3. **Повтор запросов и гонки** (двойное подтверждение, повтор `task_id`). Идемпотентность на уровне ограничений БД, одноразовое подтверждение.

## Известные ограничения

- Нет настоящей аутентификации, `confirm` может отправить любой, знающий `confirmation_id`.
- У подтверждения нет срока действия.
- `GET /tasks/{id}` не проверяет принадлежность к workspace (нет пользовательских сессий).
- Отмена во время вызова инструмента не откатывает уже выполненную запись.
- Один процесс: очередь задач в памяти (состояние в БД), горизонтального масштабирования нет.
- `LlmPlanner` не проверялся на реальной модели.
